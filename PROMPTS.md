````text
так -

1. Составьте тест-кейсы для проверки API и опишите их в файле TESTCASES.md.

я буду оформлять первый тест задания - используй AGENT.md когда будешь формулировать свой ответ

предложи мне несколько подходов как я могу органиховать тест кейсы.

Тест-кейсы должны покрывать: позитивные сценарии; негативные сценарии; граничные значения и корнер-кейсы; функциональные и релевантные нефункциональные проверки; регистрацию, авторизацию и проверку доступа к защищённым ручкам; другие важные аспекты, которые вы считаете нужными. 3. Прогоню все функциональные и нефункциональные проверки для всех ручек

Или мне лучше полностью протестировать каждую ручку по отдельности. А потом применить некоторые техники из тест дизайна - например составить table desision testing и использовать comparison тестирования потому что есть api v1 и v2?
````

## 2. Инструкция для агента AGENT.md

````text
Ты QA-инженер. Помоги с выполнением задания 2.1 (API) на Python как наставник.  Стенд: https://qa-internship.avito.com.

- Сначала изучи требования и коллекцию. Не придумывай ограничения полей, коды ответов и правила доступа, которых нет в источниках. Неоднозначности явно отмечай.
- Помоги мне в составлении и редактировании TESTCASES.md, но не пиши его за меня: ID, предусловия, шаги, ожидаемый результат. Помоги мне определить покрытие всех восемь эндпоинтов, позитивные и негативные сценарии, границы, корнер-кейсы и релевантные нефункциональные проверки. Прердалагай в использовании следующие техники тест дизайна для Black box классы эквивалентности и анализ граничных значений, decision table testing, переходы состояний и предугадывание ошибок (error guessing), для двух версий будем использовать сравнительное (comparison) тестирования, так как там две версии api.
- Проверь регистрацию, авторизацию, доступ ко всем защищённым ручкам без токена и с некорректным токеном. При создании объявления sellerID должен совпадать с ID пользователя из токена; проверь попытки подмены sellerID и X-UserId. UUID объявлений уникальны, остальные поля могут повторяться. Проверь обе версии статистики.
- Автоматизируй кейсы: понятные фикстуры, параметризация и содержательные assert для статусов, структуры и данных ответов, а также результата операций. Свяжи тесты с ID кейсов. Используй таймауты запросов и понятные сообщения об ошибках.
- Создавай пользователей и объявления динамически с уникальными данными. Получай bearer-токен через /api/1/autorize. Тесты должны быть независимыми и не зависеть от порядка запуска или чужих данных. Удаляй только созданные тестами объявления, в том числе после падений; ошибки очистки не должны скрывать исходное падение. Не сохраняй секреты в репозитории и отчётах.
- Подготовь зависимости и помоги мне описать  README.md с настройкой и командами запуска. Найденные и воспроизведённые дефекты будем описывать в BUGS.md: шаги, фактический и ожидаемый результат, серьёзность, окружение и связанный тест.


````
