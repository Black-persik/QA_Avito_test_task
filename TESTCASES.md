# Тест-кейсы API

Карточки тест-кейсов размещаются в соответствующих разделах. Каждый кейс имеет уникальный ID вида `API-01`. Название описывает конкретный сценарий; URL и метод указываются в блоке запроса.


## Общие условия и подготовка данных

- `{{baseUrl}}` — `https://qa-internship.avito.com`.
- Значения в двойных фигурных скобках подставляются при подготовке запроса.
- Во всех POST-запросах карточек передаются `Content-Type: application/json` и `Accept: application/json`.
- В GET- и DELETE-запросах карточек передаётся `Accept: application/json`; `Content-Type` не задаётся, поскольку тело запроса отсутствует. Заголовок `Authorization` передаётся или исключается согласно сценарию кейса.
- В негативных ответах защищённых ручек с HTTP-кодом 4xx или 5xx ожидается JSON-объект ошибки. Если поле `status` присутствует, его значение должно совпадать с HTTP-кодом после приведения к строке: например, HTTP `400` и `"status": "400"`. Если поля `status` нет, сравнение пропускается; проверка ожидаемого HTTP-кода выполняется всегда. 
- UUID используется как идентификатор объявления (`itemId`). `sellerID` — идентификатор пользователя из ответа регистрации; в примере коллекции он представлен числом `123`.
- `{{username}}` генерируется заново для каждого запуска; .
- `{{password}}` — тестовый пароль, подготовленный по образцу Postman-коллекции. Пароли и токены в файле обозначаются переменными.
- Для создания объявления `{{sellerID}}` берётся из ответа регистрации, а `{{accessToken}}` — из авторизации этого же пользователя, кроме намеренной подмены в `API-08`.
- `{{itemName}}` — уникальное название для текущего запуска, если поле `name` присутствует в запросе.
- В кейсах с созданием объявлений сохраняются их UUID.

## Неоднозначности требований и допущения

- **Наблюдение — чтение объявлений другого продавца:** для `GET /api/1/{sellerID}/item` источники не определяют, ограничено ли чтение владельцем или доступно любому авторизованному пользователю. **Допущение:** при доступе только владельцу запрос с токеном B к объявлениям A должен завершаться `403 Forbidden`. Проверка временно исключена из тест-кейсов и автотестов.

- **Наблюдение — удаление объявления другого пользователя:** для `DELETE /api/2/item/{id}` в источниках не определено, вправе ли пользователь B удалить объявление A, зная его UUID. **Допущение:** удаление разрешено владельцу или явно уполномоченному пользователю; при отсутствии таких прав запрос B должен быть отклонён, а объявления A и B должны сохраниться. Проверка временно исключена из тест-кейсов и автотестов.

## Регистрация — POST /api/1/register

### API-01

**Название:** Успешная регистрация нового пользователя

**Тип:** Функциональный, позитивный

**Предусловия:**

1. Подготовлен уникальный username, который ещё не зарегистрирован.
2. Подготовлен тестовый пароль.

**Запрос:**

- URL: `{{baseUrl}}/api/1/register`
- Метод: `POST`
- Заголовки: `Content-Type: application/json`, `Accept: application/json`.
- Тело запроса:

```json
{
  "username": "{{username}}",
  "password": "{{password}}"
}
```

**Шаги:**

1. Подставить подготовленные username и password в JSON-тело запроса.
2. Отправить запрос с указанными URL, методом и заголовками.

**Ожидаемый ответ:**

- Код ответа: `201 Created`.
- Тело ответа: JSON-объект с непустым `id` пользователя и `username`, совпадающим с переданным значением.


### API-02

**Название:** Регистрация без имени пользователя или пароля

**Тип:** Функциональный, граничый

**Предусловия:**

1. Регистрация выполняется без авторизации.
2. Подготовлены уникальный username и тестовый пароль по образцу коллекции.

**Запрос:**

- URL: {{baseUrl}}/api/1/register
- Метод: POST
- Заголовки: `Content-Type: application/json`, `Accept: application/json`.
  Заголовок Authorization отсутствует.
- Тело запроса зависит от варианта.

Вариант API-02a — отсутствует поле username:

```json
{
  "password": "{{password}}"
}
```

Вариант API-02b — отсутствует поле password:

```json
{
  "username": "{{username}}"
}
```

Вариант API-02с — пустой json:

```json
{
  
}
```

**Шаги:**

1. Подготовить JSON для выбранного варианта: проверяемое поле
   полностью исключить, второе заполнить корректным значением.
2. Отправить запрос регистрации.
3. Каждый вариант выполнить независимо.

**Ожидаемый ответ:**

- Код ответа: 400 Bad Request.
- Тело ответа: ошибка регистрации. 



### API-03

**Название:** Повторная регистрация пользователя с уже зарегистрированным username

**Тип:** Функциональный, негативный

**Предусловия:**

1. Для текущего теста сгенерирован уникальный username и подготовлен тестовый пароль.
2. Пользователь с этими данными зарегистрирован через `POST /api/1/register`; получен ответ `201 Created`.

**Запрос:**

- URL: `{{baseUrl}}/api/1/register`
- Метод: `POST`
- Заголовки: `Content-Type: application/json`, `Accept: application/json`. Заголовок `Authorization` отсутствует.
- Тело запроса:

```json
{
  "username": "{{username}}",
  "password": "{{password}}"
}
```

**Шаги:**

1. Подставить в JSON-тело username и password пользователя, созданного в предусловиях.
2. Повторно отправить запрос регистрации с теми же данными.

**Ожидаемый ответ:**

- Код ответа: `409 Conflict`.
- Тело ответа: ошибка, указывающая, что пользователь уже существует. Точная структура и текст ошибки в коллекции не описаны.

## Авторизация — POST /api/1/autorize

- URL: `{{baseUrl}}/api/1/autorize`

  "username": "{{username}}",

## Создание объявления — POST /api/1/item

### API-07

**Название:** Успешное создание объявления зарегистрированным и авторизованным пользователем

**Тип:** Функциональный, позитивный

**Предусловия:**

1. Для текущего теста зарегистрирован пользователь с уникальным username; его `id` сохранён в `{{sellerID}}`.
2. Этот же пользователь авторизован через `POST /api/1/autorize`; получен действительный `{{accessToken}}`.
3. Подготовлено уникальное название `{{itemName}}`.

**Запрос:**

- URL: `{{baseUrl}}/api/1/item`
- Метод: `POST`
- Заголовки: `Content-Type: application/json`, `Accept: application/json`, `Authorization: Bearer {{accessToken}}`.
- Тело запроса:

```json
{
  "sellerID": {{sellerID}},
  "name": "{{itemName}}",
  "price": 9900,
  "statistics": {
    "likes": 21,
    "viewCount": 11,
    "contacts": 43
  }
}
```

**Шаги:**

1. Подготовить JSON-тело с id авторизованного пользователя, названием и остальными данными по образцу коллекции.
2. Отправить запрос создания объявления с токеном этого пользователя.
3. Извлечь UUID объявления из поля `status` ответа и сохранить в `{{itemId}}` для проверки.
4. Отправить `GET /api/1/item/{{itemId}}` с тем же токеном и сверить полученное объявление с запросом создания.

**Ожидаемый ответ:**

- Код ответа на создание: `200 OK`, согласно примеру коллекции.
- Тело ответа на создание: JSON-объект с полем `status`, содержащим сообщение об успешном сохранении и корректный UUID объявления.
- Получение по сохранённому UUID возвращает `200 OK` и массив с одним объявлением.
- UUID, идентификатор продавца, название и цена полученного объявления соответствуют созданному объявлению и переданным данным.

### API-08

**Название:** Попытка пользователя B создать объявление от имени пользователя A подменой sellerID

**Тип:** Функциональный, негативный; проверка доступа

**Предусловия:**

1. Для текущего теста зарегистрированы два разных пользователя A и B с уникальными username; их id сохранены в `{{sellerIDA}}` и `{{sellerIDB}}`.
2. Оба пользователя авторизованы; получены действительные `{{accessTokenA}}` и `{{accessTokenB}}`.
3. Подготовлено уникальное название `{{itemName}}`; остальные поля соответствуют примеру коллекции.

**Запрос:**

- URL: `{{baseUrl}}/api/1/item`
- Метод: `POST`
- Заголовки: `Content-Type: application/json`, `Accept: application/json`, `Authorization: Bearer {{accessTokenB}}`.
- Тело запроса содержит `sellerID` пользователя A:

```json
{
  "sellerID": {{sellerIDA}},
  "name": "{{itemName}}",
  "price": 9900,
  "statistics": {
    "likes": 21,
    "viewCount": 11,
    "contacts": 43
  }
}
```

**Шаги:**

1. Получить списки объявлений A и B через `GET /api/1/{{sellerIDA}}/item` и `GET /api/1/{{sellerIDB}}/item`, используя соответствующие токены. Запомнить UUID объявлений до проверки.
2. Подготовить запрос с действительным токеном B и `sellerID` пользователя A.
3. Отправить запрос создания объявления.
4. Повторно получить списки объявлений обоих пользователей с их токенами и проверить отсутствие нового объявления из тестового запроса.

**Ожидаемый ответ:**

- Создание отклонено. Конкретный HTTP-код для подмены `sellerID` требует уточнения; в коллекции перечислены возможные ошибки `400` и `401` без привязки к этому случаю.
- Тело ответа: ошибка создания или доступа. Возвращаемый статус ошибки в теле ответа совпадает с кодом ошибки ответа.
- Объявление из тестового запроса не создано ни у пользователя A, ни у пользователя B.

### API-09

**Название:** Создание объявления без названия, цены или статистики

**Тип:** Функциональный, негативный

**Предусловия:**

**Запрос:**

- URL: `{{baseUrl}}/api/1/item`
- Метод: `POST`
- Заголовки: `Content-Type: application/json`, `Accept: application/json`, `Authorization: Bearer {{accessToken}}`.
- Тело запроса зависит от варианта. В каждом варианте отсутствует только одно проверяемое поле.

Вариант API-09a — отсутствует поле name:

```json
{
  "sellerID": {{sellerID}},
  "price": 9900,
  "statistics": {
    "likes": 21,
    "viewCount": 11,
    "contacts": 43
  }
}
```

Вариант API-09b — отсутствует поле price:

```json
{
  "sellerID": {{sellerID}},
  "name": "{{itemName}}",
  "statistics": {
    "likes": 21,
    "viewCount": 11,
    "contacts": 43
  }
}
```

Вариант API-09c — отсутствует поле statistics:

```json
{
  "sellerID": {{sellerID}},
  "name": "{{itemName}}",
  "price": 9900
}
```

**Шаги:**

1. Получить список объявлений тестового пользователя через `GET /api/1/{{sellerID}}/item` с его токеном и запомнить UUID до проверки.
2. Подготовить JSON выбранного варианта: полностью исключить проверяемое поле, остальные заполнить по образцу коллекции. `sellerID` должен совпадать с id пользователя из токена.
3. Отправить запрос создания объявления.
4. Повторно получить список объявлений этого пользователя и проверить, не появилось ли объявление из тестового запроса.
5. Каждый вариант выполнить независимо, со своей подготовкой данных.

**Ожидаемый ответ:**

- Предварительное ожидание: `400 Bad Request` и отказ в создании объявления, если отсутствующее поле обязательно.
- Тело ответа: ошибка валидации запроса. Точная структура и текст ошибки в коллекции не описаны.
- При обязательности проверяемого поля новое объявление не создаётся.
- Ожидания предварительные и применимы только после подтверждения обязательности проверяемого поля. Для необязательных полей нужно уточнить поведение и значения по умолчанию.

## Получение объявления — GET /api/1/item/{id}

### API-10

**Название:** Получение одного объявления по его UUID

**Тип:** Функциональный, позитивный

**Предусловия:**

1. Для текущего теста зарегистрирован пользователь с уникальным username и получен его действительный `{{accessToken}}` через `POST /api/1/autorize`.
2. Через `POST /api/1/item` созданы два объявления этого пользователя с разными уникальными названиями. Сохранены UUID обоих объявлений и переданные при создании данные.
3. UUID запрашиваемого объявления сохранён в `{{itemId}}`, второго — в `{{otherItemId}}`.

**Запрос:**

- URL: `{{baseUrl}}/api/1/item/{{itemId}}`
- Метод: `GET`
- Заголовки: `Accept: application/json`, `Authorization: Bearer {{accessToken}}`.
- Тело запроса: отсутствует.

**Шаги:**

1. Подставить UUID первого объявления в URL запроса.
2. Отправить запрос с действительным токеном создавшего объявления пользователя.
3. Проверить количество объявлений в ответе и сверить возвращённые данные с данными запрошенного объявления.

**Ожидаемый ответ:**

- Код ответа: `200 OK`.
- Тело ответа: JSON-массив ровно с одним объявлением, согласно описанию ручки в коллекции.
- UUID объявления совпадает с `{{itemId}}`.
- Название, цена и идентификатор продавца соответствуют данным, использованным при создании запрошенного объявления.
- Второе объявление с UUID `{{otherItemId}}` в ответе отсутствует.

### API-11

**Название:** Получение объявления по корректному UUID, которому не соответствует существующее объявление

**Тип:** Функциональный, негативный

**Запрос:**

- URL: `{{baseUrl}}/api/1/item/{{missingItemId}}`
- Метод: `GET`
- Заголовки: `Accept: application/json`, `Authorization: Bearer {{accessToken}}`.
- Тело запроса: отсутствует.

**Шаги:**

1. Подставить сгенерированный корректный UUID в URL запроса.
2. Отправить запрос с действительным токеном.

**Ожидаемый ответ:**

- Код ответа: `404 Not Found`, из числа ответов, перечисленных в коллекции для этой ручки.
- Тело ответа: ошибка, указывающая, что объявление не найдено. Возвращаемый статус ошибки в теле ответа совпадает с кодом ошибки ответа.
- Данные существующих объявлений не возвращаются.

### API-12

**Название:** Получение объявления с идентификатором неправильного формата

**Тип:** Функциональный, негативный

**Предусловия:**

## Релевантные нефункциональные проверки

### API-30

**Название:** Отказ в доступе к объявлению с неверной подписью JWT

**Тип:** Нефункциональный (безопасность), негативный

**Предусловия:**

1. Для текущего теста зарегистрирован пользователь с уникальным username и получен его действительный JWT через `POST /api/1/autorize`; исходный токен сохранён в `{{accessToken}}`.
2. Этим пользователем создано объявление с уникальным названием и его sellerID. Существующий корректный UUID сохранён в `{{itemId}}`, а переданные данные - для проверки ответа.
3. Исходный JWT имеет формат `header.payload.signature`: три части, разделённые двумя точками.

**Запрос:**

- URL: `{{baseUrl}}/api/1/item/{{itemId}}`
- Метод: `GET`
- Заголовки: `Accept: application/json`, `Authorization: Bearer {{tamperedToken}}`.
- Тело запроса: отсутствует.

**Шаги:**

1. Выполнить контрольный GET объявления с исходным `{{accessToken}}` и убедиться, что получен `200 OK` с данными созданного объявления.
2. Скопировать исходный JWT в отдельную переменную `{{tamperedToken}}`, сохранив `{{accessToken}}` без изменений.
3. В `{{tamperedToken}}` заменить первый символ третьей части, сразу после второй точки: латинскую `A` заменить на `B`, любой другой символ — на латинскую `A`. Остальные символы и обе точки сохранить. Полученный токен должен отличаться от исходного только одним символом подписи.
4. Отправить основной GET с `{{tamperedToken}}`. Убедиться, что передаётся единственный заголовок `Authorization` с изменённым токеном и исходный токен коллекции не подставляется вместо него.
5. Повторить контрольный GET с исходным `{{accessToken}}`, чтобы подтвердить его действительность после проверки.

**Ожидаемый ответ:**

- Код ответа основного запроса с неверной подписью JWT: `401 Unauthorized`.
- Тело ответа: ошибка аутентификации. Точная структура и текст ошибки в источниках не описаны.
- Данные объявления по JWT с неверной подписью не выдаются.
- Контрольные запросы с исходным токеном до и после проверки возвращают `200 OK` и данные объявления с запрошенным UUID, названием, ценой и идентификатором продавца, соответствующими подготовленным данным.
